Yes. I’d make both of these first-class simulation concepts rather than layering them onto the existing `SpawnAreaEvent`/`StatusInstance` logic.

### 1. Make `Cast` a real runtime concept

I’d distinguish **an event that starts something** from **the cast/action itself**.

A cast represents:

* who is casting
* what it is called
* when it started
* how long until completion
* whether it appears in the UI
* what happens on completion

Something along these lines:

```ts
export interface CastDefinition {
  id: string;
  name: string;
  castTime: number;
  visible: boolean;
  effects: CastEffect[];
}

export interface ActiveCast {
  definitionId: string;
  sourceId: string;
  startedAt: number;
  completesAt: number;
}
```

I'd keep the **definition** immutable and the `ActiveCast` as runtime state.

Then the event becomes very small:

```ts
export interface StartCastEvent extends BaseEvent {
  type: 'start_cast';
  source: string;
  cast: string;
}
```

The executor starts the cast, and the simulation resolves it when `completesAt` is reached.

That gives you a clean timeline:

```text
t=10.0  boss starts "Blazing Strike"
        ↓
        UI shows cast bar
        ↓
t=12.5  cast completes
        ↓
        cone damage resolves
```

### Cast effects

I'd avoid putting arbitrary simulation behavior directly into `CastDefinition`. Instead, give it the same kind of declarative effect system you're already moving toward:

```ts
export type CastEffect =
  | DamageEffect
  | SpawnAreaEffect
  | ApplyStatusEffect
  | StartCastEffect
  | RemoveStatusEffect;
```

For example:

```ts
{
  "id": "blazing-strike",
  "name": "Blazing Strike",
  "castTime": 2.5,
  "visible": true,
  "effects": [
    {
      "type": "cone",
      "target": "in_front",
      "radius": 20,
      "angle": 90,
      "damage": {
        "amount": 1000,
        "type": "fire"
      }
    }
  ]
}
```

The important bit is that **the cast owns the semantic identity of the action**.

So damage records can say:

```text
12.50  Alice was hit by Blazing Strike for 1000 fire damage
```

rather than:

```text
12.50  Alice was hit by effect-17
```

I'd actually carry the cast/action identity through resolution:

```ts
export interface DamageSource {
  type: 'cast' | 'status' | 'event';
  id: string;
  name: string;
}
```

That will pay off substantially once you have an event log/replay system.

## The random ice/fire mechanic

I agree with your instinct that the randomness shouldn't live as two unrelated properties on an area effect.

There are a few levels of abstraction here.

### Simple version

Have the timeline choose a cast:

```json
{
  "type": "random_choice",
  "choices": [
    { "cast": "blazing-strike" },
    { "cast": "frigid-strike" }
  ]
}
```

And each cast has its own targeting:

```json
{
  "id": "blazing-strike",
  "name": "Blazing Strike",
  "castTime": 2.5,
  "visible": true,
  "effects": [
    {
      "type": "cone",
      "direction": "in_front",
      "angle": 90,
      "radius": 20,
      "damage": {
        "amount": 1000,
        "type": "fire"
      }
    }
  ]
}
```

That is already much better than:

```json
{
  "element": "random",
  "direction": "random"
}
```

because the encounter is now describing **what the boss is doing**, rather than exposing implementation variables.

### But I particularly like your `Flamefrost` idea

If the mechanic is actually perceived by the player as one named mechanic with two sequential hits, I'd model that as one cast:

```json
{
  "id": "flamefrost",
  "name": "Flamefrost",
  "castTime": 3.0,
  "visible": true,
  "effects": [
    {
      "type": "delayed",
      "delay": 0,
      "effect": {
        "type": "cone",
        "direction": "in_front",
        "angle": 180,
        "damage": {
          "amount": 1000,
          "type": "fire"
        }
      }
    },
    {
      "type": "delayed",
      "delay": 1.0,
      "effect": {
        "type": "cone",
        "direction": "behind",
        "angle": 180,
        "damage": {
          "amount": 1000,
          "type": "ice"
        }
      }
    }
  ]
}
```

Then the randomization can choose between variants:

```text
Flamefrost
  ├── front = fire, back = ice
  └── front = ice,  back = fire
```

Or potentially randomize the **orientation** independently:

```text
Flamefrost
  ├── fire front → ice back
  ├── fire back  → ice front
  └── ...
```

The key architectural point is that **randomization should select/parameterize a mechanic, not define the mechanic's underlying geometry**.

# 2. Untimed statuses

This should be a very small change to the status model.

You already have:

```ts
expiresAt?: number;
```

and you're effectively using `undefined` to mean permanent.

I'd make that semantic explicit:

```ts
export interface StatusInstance {
  definitionId: string;
  appliedAt: number;
  expiresAt?: number;
  stacks: number;
}
```

So:

```json
{
  "status": "protected"
}
```

means it remains until explicitly removed.

Where I'd make the bigger change is to the **status definition**.

---

# 3. Status removal needs to be an actual event

Add:

```ts
export interface RemoveStatusEvent extends BaseEvent {
  type: 'remove_status';
  target: PlayerSelector;
  status: string;
}
```

Then:

```json
{
  "type": "remove_status",
  "target": {
    "type": "role",
    "role": "damage"
  },
  "status": "protected"
}
```

The executor should go through a single status-removal path rather than directly filtering the array.

Something like:

```ts
removeStatus(player, statusId)
```

That matters because **removing a status is now a meaningful simulation event**.

---

# 4. Statuses can trigger effects when removed

I'd put this on `StatusDefinition`, not `StatusInstance`.

For example:

```ts
export interface StatusDefinition {
  id: string;
  name: string;

  onApply?: StatusTrigger;
  onExpire?: StatusTrigger;
  onRemove?: StatusTrigger;
}
```

Although I'd probably simplify this to:

```ts
export interface StatusDefinition {
  id: string;
  name: string;
  onRemove?: StatusEffect[];
}
```

Initially.

For example:

```json
{
  "id": "volatile",
  "name": "Volatile",
  "onRemove": [
    {
      "type": "start_cast",
      "cast": "volatile-explosion"
    }
  ]
}
```

Now there are two ways the status can disappear:

```text
                    ┌── timer expires
                    │
Status ─────────────┤
                    │
                    └── remove_status event
                              │
                              ▼
                       removeStatus()
                              │
                              ▼
                         onRemove
```

Both paths converge on the same logic.

That's important because otherwise you'll eventually get bugs where:

> "The status disappearing naturally triggered the explosion, but manually removing it didn't."

There should be exactly one status-removal pipeline.

---

# 5. Expiration should also be an event internally

I'd go one step further and make the simulation treat expiration as a status lifecycle operation:

```ts
private expireStatuses(): void {
  for (const player of this.state.players) {
    for (const status of player.statuses) {
      if (
        status.expiresAt !== undefined &&
        status.expiresAt <= this.state.time
      ) {
        this.removeStatus(player, status.definitionId);
      }
    }
  }
}
```

Then:

```ts
private removeStatus(player: Player, statusId: string): void {
  const index = player.statuses.findIndex(
    status => status.definitionId === statusId
  );

  if (index === -1) return;

  const [status] = player.statuses.splice(index, 1);

  this.statusExecutor.onRemoved(player, status);
}
```

This gives you a very useful invariant:

> **A status is never removed without going through `removeStatus`.**

That will become increasingly valuable as statuses gain more behavior.

---

# 6. Status-triggered casts

I'd avoid making statuses directly call `MechanicExecutor`.

Instead, have their effects enter the same execution machinery as everything else.

For example:

```ts
export interface StartCastEffect {
  type: 'start_cast';
  cast: string;
}
```

Then:

```text
status removed
      ↓
StatusExecutor
      ↓
StartCastEffect
      ↓
CastSystem
      ↓
ActiveCast
      ↓
cast completes
      ↓
Cast effects
```

That keeps the architecture composable.

Eventually you'll be able to have:

```text
Timeline event
    ↓
ApplyStatus
    ↓
Status expires
    ↓
StartCast
    ↓
Cast completes
    ↓
ApplyStatus
    ↓
Status removed
    ↓
Damage
```

without each subsystem needing special knowledge of the others.

## One architectural adjustment I'd make now

With these additions, I think the simulation is naturally separating into four concepts:

```text
Timeline
   │
   ├── starts casts
   ├── applies/removes statuses
   └── recalculates roles/positions
          │
          ▼
     Runtime systems
          │
    ┌─────┼─────────┐
    ▼     ▼         ▼
  Cast  Status    Bots
    │     │
    └─────┴─── effects
                 │
                 ▼
             Game State
```

And I'd make **casts and statuses first-class runtime objects**, while effects remain the lower-level things that actually modify the world.

That gives you a fairly clean vocabulary:

* **Event** — something scheduled by the encounter timeline.
* **Cast** — an action performed by an entity, potentially with a cast time.
* **Status** — persistent state attached to an entity.
* **Effect** — an operation that changes simulation state.
* **Area** — a spatial effect that persists for some duration.
* **Condition/Selector** — determines who/what something applies to.
* **Mechanical role** — derived behavioral state used by players/bots.

I think this is a good point to establish those boundaries before adding much more simulation functionality.
